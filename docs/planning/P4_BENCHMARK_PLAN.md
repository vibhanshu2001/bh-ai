# Bhai — Phase P4 Benchmark Plan: Context Efficiency & Reliability

**Document ID:** P4-BENCH-001  
**Phase:** P4 — Project Memory & Context Engine  
**Status:** Evaluation Protocol  
**Target Platform:** macOS 14+ (Sonoma, Sequoia), Apple Silicon (`arm64`)  

---

## 1. Benchmark Objectives & Ground Rules

Phase P4 must demonstrate measurable usefulness. Claims of token reduction or discovery acceleration cannot be based on speculative projections.

**Core Evaluation Hypothesis:**  
Providing coding agents with structured, prebaked, task-specific Context Packs from Bhai Memory significantly reduces input discovery tokens and initial tool calls without degrading task correctness, violating local privacy, or polluting project knowledge.

### Non-Negotiable Benchmarking Rules
1. **No Made-Up Target Numbers:** Do not claim a blanket "80% or 90% token reduction" in documentation before empirical evaluation. Success means **lower net rediscovery effort with zero material degradation in task correctness**.
2. **Reproducible Environment:** Automated test harnesses (`scripts/run_p4_benchmarks.js`) must run on a standardized local fixture repository with frozen initial states.
3. **Multi-Trial Execution:** Run a minimum of 3 trials per task scenario to account for LLM non-determinism.

## 2. Compared Baselines

| Baseline ID | Name | Configuration & Context Delivery |
| :--- | :--- | :--- |
| **Baseline A** | **Normal Agent Discovery** | The agent begins in the project root with an empty initial prompt. It must discover architecture, dependencies, services, and files using raw filesystem and terminal tool calls (`ls`, `find`, `cat`, `grep`). |
| **Baseline B** | **Static Project Documentation** | The agent is provided with a standard static `AGENTS.md` or `README.md` file in the project root containing human-written instructions and architecture overviews. |
| **Baseline C** | **Bhai Context Engine** | The agent calls `yebata` upon startup via local MCP, receiving a prebaked Quick or Task Context Pack tailored to the active task. |

## 3. Evaluated Metrics & Measurement Methodology

### 3.1 Token & Tool Consumption Metrics
1. **Total Input Tokens:** Sum of all prompt and context tokens consumed across the entire task session.
2. **Total Output Tokens:** Sum of tokens generated by the model.
3. **Discovery-Specific Tokens:** Tokens consumed strictly prior to the first code-modifying tool call.
4. **Agent Discovery Tool Calls:** Number of exploratory read operations (`read_file`, `list_directory`, `search_files`) executed before productive editing.
5. **Context Retrieval Overhead:** Tokens consumed by MCP tool requests and schemas.
6. **MCP Checkpoint Overhead:** Cumulative tokens consumed by sending milestone checkpoints during development.

### 3.2 Task Performance & Timing Metrics
1. **Time to Productive Work (TTPW):** Wall-clock seconds elapsed from session start until the agent executes its first code edit or creates its first file.
2. **Total Task Duration:** Total wall-clock time (seconds) to reach completion.
3. **Context Pack Generation Latency:** Milliseconds required by Bhai Utility Process to generate and return a requested pack.

### 3.3 Quality & Correctness Metrics
1. **Task Completion Correctness:** Evaluated against an automated test suite verifying functional requirements (0% to 100% pass rate).
2. **Fact Recovery Accuracy:** Percentage of ground-truth architectural rules and conventions successfully respected (e.g., using RS256 instead of HS256, placing files in `src/services` instead of `src/controllers`).
3. **Missing Critical Facts:** Number of mandatory project constraints violated.
4. **Stale Fact Rejection:** When presented with deliberately stale file references in context, does the agent detect and re-verify, or hallucinate edits?

### 3.4 System Resource Metrics
1. **Compaction CPU Overhead:** Peak CPU % during deterministic and local model compaction.
2. **Compaction Memory Overhead:** Peak RSS memory delta during compaction.
3. **SQLite Storage Growth:** Database size delta in KB after 100 checkpoints and compaction.

## 4. The Six Benchmark Scenarios

### Scenario 1: Fresh Project Onboarding Task
- **Context:** An agent is tasked with adding a healthcheck route to an unfamiliar multi-service monorepo.
- **Evaluation:** Compare tokens and tool calls between Baseline A (unassisted), Baseline B (README), and Baseline C (Bhai Quick Context Pack).

### Scenario 2: Resumed Unfinished Task
- **Context:** Task was started by a previous agent session and left in an incomplete state (halfway through adding database migrations).
- **Evaluation:** Does Baseline C allow immediate continuation from the recorded active task and checkpoint state without re-inspecting all prior files?

### Scenario 3: Architecture-Heavy Refactoring
- **Context:** Refactor database client imports across multiple services subject to strict architectural decision records (ADRs) forbidding direct connection pooling in child workers.
- **Evaluation:** Does Baseline C enforce the architectural decision and prevent prohibited imports?

### Scenario 4: Cross-Agent Continuation (Claude Code -> Codex)
- **Context:** Claude Code builds an authentication middleware and saves a structured handoff via `handoffsavekar`. Codex is launched in a fresh terminal to build the user profile endpoint.
- **Evaluation:** Measure how quickly Codex identifies the completed auth work and utilizes the RS256 token verifier without re-implementing auth.

### Scenario 5: Stale-Context Resilience
- **Context:** A previously referenced service directory was renamed or moved. The memory engine flags the path as `(stale reference)`.
- **Evaluation:** Verify that the agent checks current Git status and updates the path rather than failing or creating files in the old location.

### Scenario 6: High-Frequency Compaction Stress
- **Context:** A synthetic session generates 150 milestone checkpoints in rapid succession.
- **Evaluation:** Verify that deterministic compaction triggers at thresholds, reduces token volume by >=60%, and retains 100% of decisions and active blockers.

## 6. Real-World Integration & Acceptance Test Matrix (Tests A–L)

To validate the bidirectional Guiding Skill and continuous context exchange workflow (see [P4_AGENT_INTEGRATION.md](../architecture/P4_AGENT_INTEGRATION.md)), the evaluation suite executes 12 mandatory real-world test cases:

| Test ID | Test Name | Operational Scenario | Expected Success Criteria |
|---|---|---|---|
| **Test A** | **Context Retrieval** | Claude Code starts in a registered Bhai project and requests context. | Calls `yebata`; receives valid Task Pack (<1,500 tokens); benchmark evaluates hypothesis of $\ge 50\%$ reduction in discovery calls. |
| **Test B** | **Mid-Session Checkpoint** | Claude makes a major architectural decision during active coding. | Calls `yesavekar` (decision.proposed); target server latency $<25$ ms; session continues without interruption. |
| **Test C** | **Multiple Checkpoints** | Claude submits rapid progress updates across multiple iterations. | Repeated idempotency keys return existing IDs; state changes merge; redundant progress is superseded. |
| **Test D** | **Cross-Agent Continuation** | Codex launches in a fresh terminal on a task previously started by Claude. | Calls `kahanthe`; recovers dirty files and next steps; continues work without repeating completed code. |
| **Test E** | **Pre-Compaction Preservation** | Agent detects context window pressure or receives `/compact`. | Calls `handoffsavekar` or `yesavekar(handoff.prepared)`; working memory is preserved before local context is reset. |
| **Test F** | **Abrupt Termination** | Agent process crashes or terminal is killed mid-task (SIGKILL). | In-flight transaction rolls back cleanly; all previously committed checkpoints remain intact in SQLite. |
| **Test G** | **Long-Running Session** | A 2-hour coding session with 40 milestone checkpoints. | Checkpoint frequency targets $2\text{--}6$/hr; target average payload $<250$ tokens; SQLite DB growth $<1.5$ MB; 0 memory leaks. |
| **Test H** | **Offline Operation** | Mac network interface disabled (`networksetup -setairportpower off`). | Bhai MCP server, SQLite storage, Layer A compaction, and retrieval run 100% locally with zero errors or timeouts. |
| **Test I** | **Skill Installation** | Agent Integration Kit installs, updates, and uninstalls the guiding skill. | `~/.claude.json` / `~/.codex/config.toml` modified non-destructively; unrelated config preserved; clean rollback on uninstall. |
| **Test J** | **Unavailable Bhai** | Agent starts when the Bhai desktop application is NOT running. | MCP adapter returns immediate error; agent follows skill guidance and continues normal development without hanging. |
| **Test K** | **Authorization Enforcement** | Agent without `write_checkpoints` grant attempts to record a checkpoint. | Request rejected with `PERMISSION_DENIED`; audit log records security rejection; no database rows modified. |
| **Test L** | **Token Efficiency ROI** | Measure total MCP overhead tokens vs downstream discovery savings across 10 sessions. | Evaluates benchmark hypothesis of Net ROI ratio ($\frac{\text{Tokens Saved}}{\text{Tokens Spent}}$) $\ge 4.0\times$; target checkpoint call overhead $<250$ tokens. |
